# 领域文档规范 (Domain Docs)

定义工程技能在探索和理解本代码库时，如何使用领域文档与架构决策记录。

## 探索代码库前的先验阅读准则

在开展具体模块研发与探索前，必须首先按需查阅：

- 项目根目录下的 **`CONTEXT.md`**（若存在）；
- 若根目录存在 **`CONTEXT-MAP.md`**，则查阅其中关联的各个子上下文 `CONTEXT.md`，按需阅读与当前任务相关的上下文文档；
- **`docs/adr/`** 目录：查阅与当前工作领域相关的架构决策记录（ADR）。在多上下文仓库中，同步检查对应子上下文目录下的 `src/<context>/docs/adr/`。

> 💡 **静默推进原则**：若上述任何文件暂不存在，**静默继续执行后续任务**，严禁主动中断报错，亦无需预先建议创建。后续通过 `/domain-modeling` 技能在领域概念或架构决策切实收敛时懒加载创建。

## 目录结构标准

### 单上下文仓库（Single-context，本项目适用）

```text
.
├── CONTEXT.md                  # 领域通用词汇表与核心模型
├── docs/
│   ├── adr/                    # 架构决策记录 (ADR)
│   │   ├── 0001-example.md
│   │   └── ...
│   └── agents/                 # Agent 交互与工程配置
└── ...
```

### 多上下文仓库（Multi-context，仅当根目录存在 CONTEXT-MAP.md 时生效）

```text
.
├── CONTEXT-MAP.md              # 上下文映射总览
├── docs/adr/                   # 全局系统级架构决策
└── src/
    ├── module-a/
    │   ├── CONTEXT.md
    │   └── docs/adr/           # 模块特定架构决策
    └── module-b/
        ├── CONTEXT.md
        └── docs/adr/
```

## 遵循领域词汇表约定

当输出涉及业务领域概念（如 Issue 标题、重构建议、技术方案、测试用例名称）时，必须严格使用 `CONTEXT.md` 中定义的标准术语，严禁使用词汇表已明确规避的近义词或生造词。

若所需业务概念尚未在词汇表中定义，这是一个明确信号：
1. 要么是在引入项目中不存在的冗余概念（应重新审视并精简）；
2. 要么确实存在领域知识缺口（应记录并适时通过 `/domain-modeling` 技能补充）。

## 架构决策冲突显式告警 (ADR Conflicts)

如果产出的方案或代码实现与现存 ADR 决策产生冲突，必须显式向上暴露，严禁静默覆盖或忽视：

> ⚠️ *该设计与 ADR-0001 (说明) 存在冲突 —— 建议重新评估并审议，原因如下：...*
